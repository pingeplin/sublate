# 2611.0001 In-App Update

**Date:** 2026-11-09
**Status:** accepted
**Author:** EP Lin

## Context

Sublate checks for a newer version of itself, but it does not install it. Today:

- `core/src/update/github.rs` (`GitHubAppReleases`) reads `releases/latest` of `pingeplin/sublate`, accepts only tags of the form `v<version>`, and derives the release page URL from the version.
- `core/src/update/app.rs` (`newer_release`) returns the release only when it is newer than the running version.
- `core/src/ffi.rs` exports `Backend::check_app_update(current_version) -> Option<AppUpdate { version, page_url }>`.
- `app/Kit/Sources/SublateUI/AppUpdateModel.swift` holds `AppUpdateState` (`unchecked`, `checking`, `upToDate`, `available`, `failed`). `SettingsView` shows a **Download…** link to the release page. The **Check for Updates…** menu item (`Views/UpdateCommands.swift`) opens Settings and starts a check.
- The user downloads the DMG from GitHub, opens it, and drags the app to Applications again.

The release is published with `gh release create v<version> dist/Sublate-<version>.dmg`. GitHub records a `sha256:<hex>` `digest` for each asset. `scripts/package.sh` already zips the app (`ditto -c -k --keepParent`) to submit it for notarization, but it does not keep that zip.

The yt-dlp updater (`core/src/update/mod.rs`) already downloads a release asset, checks its sha256, and unpacks it with `/usr/bin/ditto`. This spec reuses that approach for the app.

## Motivation

The manual update has five steps and leaves an old DMG behind. Users stay on old versions, and bug fixes do not reach them. An update that runs in one click (**Install and Relaunch**) removes this friction.

The approach is decided: a custom updater on top of the existing Rust update code, not the Sparkle framework. This keeps the dependency list short and reuses the download and checksum code that the yt-dlp updater already tests.

## Proposed Solution

### Overview

Each release also publishes `Sublate-<version>.zip`, which holds the notarized and stapled app. The update check reads the sha256 digest of that zip from the release. When the user clicks **Install and Relaunch**:

1. The Rust core downloads the zip, checks its sha256, and unpacks it into a staging folder in the cache directory.
2. The Swift app checks the code signature of the unpacked bundle against a requirement pinned to Team ID `5Q458ND242` and bundle ID `tech.radiw.sublate`, and checks that its `CFBundleShortVersionString` is the offered version.
3. The Swift app replaces the running bundle at its current path with the new bundle. If the replacement fails, the old bundle stays at (or goes back to) that path. On success, no copy of the old bundle stays in the folder that holds the running app.
4. The app arranges for the app at its current path (now the new bundle) to start once this process has exited, and then quits this process.

The app falls back to the current flow (a **Download…** link to the release page) when it cannot replace itself: the release has no zip, or the folder that holds the running app is not writable (this includes an app that runs from the DMG or that macOS runs from a translocated path).

### Key Components

- **Rust: `AppRelease` + `AppArchive`** (`core/src/update/app.rs`) — `AppRelease` gets `archive: Option<AppArchive>`. `AppArchive` holds the `sha256` of `Sublate-<version>.zip`. Its download URL is derived from the version, never read from the feed: `https://github.com/pingeplin/sublate/releases/download/v<version>/Sublate-<version>.zip`.
- **Rust: `GitHubAppReleases`** (`core/src/update/github.rs`) — `parse_app_release` reads the `Sublate-<version>.zip` asset and its `digest`. A release without that asset, or with an asset that has no `sha256:` digest, has `archive: None` (it is still a valid release; the check does not fail). `AppReleaseFeed` gets a `download` method that streams to a file and reports progress. The download uses the long download timeout (as for yt-dlp), not the 30-second check timeout.
- **Rust: `AppDownloader`** (new, `core/src/update/app.rs` or a sibling module) — given an offered version and sha256, it empties the staging folder `<cache>/app-update/`, downloads the zip there, checks the sha256, unpacks it with `/usr/bin/ditto -x -k`, deletes the zip, and returns the path of `<cache>/app-update/Sublate.app`. The zip must hold exactly one top-level item, `Sublate.app`, and that item must be a folder (not a symlink or a plain file). On any error after it emptied the staging folder, `<cache>/app-update/` exists and holds no entries.
- **Rust FFI** (`core/src/ffi.rs`) — `AppUpdate` gets `archive_sha256: Option<String>`. New method `download_app_update` and new foreign listener `AppDownloadListener`.
- **Swift: `AppUpdateBackend`** (`BackendRoles.swift`) — gets `downloadAppUpdate(update:listener:)`.
- **Swift: `AppInstaller` protocol** (new) — the seam between `AppUpdateModel` and the file system. One live implementation composed of three single-purpose parts:
  - **`BundleVerifier`** — checks the code signature (Security framework, `SecStaticCode`) of the whole bundle, nested code included, against the pinned requirement (the same result as `codesign --verify --deep --strict -R='<pinned requirement>'`), and checks that `CFBundleShortVersionString` equals the offered version as text.
  - **`BundleReplacer`** — replaces the bundle at a path with the staged bundle; restores the old bundle when a step fails. Steps (the same order Sparkle 2 uses, see A3):
    1. Move the staged bundle into a temporary folder on the same volume as the running bundle (`FileManager.url(for: .itemReplacementDirectory, in: .userDomainMask, appropriateFor: runningApp, create: true)`). `ditto` copies when the volumes differ. `FileManager.replaceItemAt` fails across volumes, so this step is required.
    2. Swap the two bundles (an atomic swap such as `renamex_np(RENAME_SWAP)`, or move old out / move new in / move old back on failure).
    3. Move the old bundle to the Trash, so the user can recover it.
    4. Set the new bundle's modification date to now, so Launch Services and Finder see the new version.
    5. Delete the temporary folder.

    Its file operations (move, swap, trash) sit behind a small injected seam, so a test can make one step fail (S16) and tests never write to the user's real Trash.
  - **`Relauncher`** — starts a detached helper outside the app (for example `/bin/sh -c 'while kill -0 <pid>; do sleep 0.2; done; /usr/bin/open <path>'`), then quits the app with `NSApplication.terminate`. The helper must wait for the old process to exit: `open` without `-n` reuses a running instance with the same bundle ID (A3). Quit soon after the swap, because `Bundle.main` still points to the old bundle in the Trash.
- **Swift: `AppUpdateModel`** — new states, the `canInstall` property, and the `install()` action. It receives the `AppInstaller` and the running bundle URL through its initializer (the app passes `Bundle.main.bundleURL`; tests pass a temp URL). The model decides what is offered; the view only reads it.
- **Swift: `Presentation.swift`** — `AppUpdateState.status` and `.downloadPage` cover the new states (see Interface Contract).
- **Swift: `SettingsView`** — shows **Install and Relaunch** when `model.canInstall` is true, a progress line while it downloads, and the **Download…** link when `state.downloadPage` is not nil and `canInstall` is false. The footer text says that Sublate can install a newer version and relaunch, and that otherwise the user downloads it from its release page.
- **Release process** — `scripts/package.sh`, when it notarizes (`make release`), zips the stapled app as `dist/Sublate-<version>.zip`, beside the DMG; the path is derived from the DMG path. `README.md` documents the new asset and the new update flow.

### Data Flow

1. User clicks **Check for Updates**. `check_app_update` returns `AppUpdate { version, page_url, archive_sha256 }` or `None`.
2. `AppUpdateModel` sets `.available(update)`. `model.canInstall` is true only when the state is `.available(update)`, `update.archiveSha256 != nil`, and `installer.canInstall(replacing: runningApp)`. The view shows **Install and Relaunch** when it is true and the **Download…** link otherwise.
3. User clicks **Install and Relaunch**. The model sets `.downloading(update, fraction: nil)` and calls `downloadAppUpdate` with the same `AppUpdate` it got from the check (never another version). Each listener call sets `fraction` to `done / total`, or to `nil` when `total` is `nil` or `0`.
4. The backend returns the path of the staged `Sublate.app`. The model sets `.installing(update)` and calls `installer.install(staged, version: update.version, replacing: runningApp)`, which verifies and then replaces.
5. On success the model sets `.readyToRelaunch(update)` and calls `installer.relaunch(runningApp)`; the process quits and the new version starts at the same path. If a job started during the download, the model does not relaunch and waits for the user to click **Relaunch** after the job ends. While the state is `.readyToRelaunch`, `check()` does nothing: the running copy has already been replaced.
6. On any error the model sets `.installFailed(update, error.userMessage)`. The view shows the message and the **Download…** link; **Install and Relaunch** is not offered again until a new check returns `.available`. The running app is unchanged. A staged bundle left behind by a failed install is removed by the next download (S9).

Swift:

```swift
protocol AppUpdateBackend: Sendable {
    func checkAppUpdate(currentVersion: String) async throws -> AppUpdate?
    func downloadAppUpdate(update: AppUpdate, listener: AppDownloadListener) async throws -> String
}

protocol AppInstaller: Sendable {
    /// False when the folder that holds `running` is not writable.
    func canInstall(replacing running: URL) -> Bool
    /// Verifies `staged` (signature requirement + version), then replaces `running` with it.
    /// On error, `running` still holds the old bundle.
    func install(_ staged: URL, version: String, replacing running: URL) async throws
    /// Arranges for the app at `app` to start once this process has exited, then quits this process.
    func relaunch(_ app: URL)
}

enum AppUpdateState: Equatable {
    case unchecked, checking, upToDate
    case available(AppUpdate)
    case downloading(AppUpdate, fraction: Double?)   // nil before the first progress report and when the size is unknown or 0
    case installing(AppUpdate)
    case installFailed(AppUpdate, String)
    case failed(String)                              // the check failed
}

@MainActor @Observable
final class AppUpdateModel {
    init(backend: any AppUpdateBackend, installer: any AppInstaller, activity: any JobActivity,
         currentVersion: String, runningApp: URL)
    private(set) var state: AppUpdateState
    /// True only in `.available(update)` with `update.archiveSha256 != nil`
    /// and `installer.canInstall(replacing: runningApp)`. It does not depend on `activity`.
    var canInstall: Bool { get }
    /// True while `activity.isBusy` is true. The view shows Install and Relaunch (or Relaunch)
    /// disabled, with a note that the current job must finish first.
    var isBlockedByJob: Bool { get }
    /// True in `.checking`, `.downloading` and `.installing`. The view disables both buttons while it is true.
    var isBusy: Bool { get }
    /// Does nothing while `isBusy` is true. Otherwise behaves as today.
    func check() async
    /// Does nothing unless `canInstall` is true and `isBlockedByJob` is false.
    /// After a successful install the state is `.readyToRelaunch(update)`, and the model relaunches at once
    /// unless a job runs. If the relaunch does not happen, **Relaunch** stays available.
    func install() async
    /// In `.readyToRelaunch` and with no job running: calls `installer.relaunch(runningApp)`. Otherwise does nothing.
    func relaunch()
}

/// What the main window is doing. `ContentModel` conforms (its existing `isBusy`).
@MainActor protocol JobActivity: AnyObject {
    var isBusy: Bool { get }
}
```

`AppUpdateState` gets one more case for the job guard: `case readyToRelaunch(AppUpdate)` — the new bundle is in place, but a job started during the download, so the relaunch waits for the user. Its `status` is `.info` and names the version; its `downloadPage` is nil. The view shows a **Relaunch** button, disabled while `isBlockedByJob` is true.

| `.installing(u)` | not `.idle`; its text names `u.version` | `nil` |
| `.installFailed(u, m)` | `.failure(m)` | `URL(u.pageUrl)` |

## Alternatives Considered

### Sparkle 2

The standard updater for macOS apps outside the App Store. It handles replacement, relaunch, and folders that need an administrator password. Not chosen: it adds a framework and an EdDSA key and appcast to the release process, while the project already has tested download and checksum code.

### Install from the DMG

Download the DMG, mount it with `hdiutil`, and copy the app out. Not chosen: mounting adds a process, a mount point to clean up, and failure modes (a mount left behind). A zip unpacks with `ditto`, which the yt-dlp updater already uses.

### Take the download URL from `browser_download_url`

Not chosen: the current code derives every URL from the checked version so that nothing the feed says is opened as it is. The archive URL follows the same rule.

## Migration & Rollback

### Migration Steps

1. Ship this feature in a release (for example 0.4.0) that also publishes `Sublate-0.4.0.zip`.
2. Users on 0.3.0 or earlier update by hand one last time: their app has no installer.
3. From then on, each release must publish the zip. A release without it still works: users see the **Download…** link (S6).

### Rollback Plan

If a release has a bad updater, publish a fixed release; users of the bad version update by hand. Removing the zip from a GitHub release makes all clients fall back to the release page, with no client change.

## Security Considerations

- **Integrity:** the sha256 from the GitHub asset `digest` detects a damaged or replaced download in transit. It does not prove who made the file: whoever can publish a release can also set its digest.
- **Authenticity:** the code-signature check with the pinned requirement is the only *identity* gate. A file that `reqwest` downloads has no quarantine attribute, so Gatekeeper does not run its notarization check or its first-launch prompt on the new app (A2). The kernel still refuses to run unsigned code on Apple Silicon, but it accepts any valid signature, ad-hoc included. The check must run on the staged bundle before any file in the install location changes.
- **Download URL:** GitHub answers the derived URL with a redirect to a signed URL that expires after about one hour. Follow the redirect on each download (reqwest does this by default); never store the redirect target.
- **Read-only DMG:** the `canInstall` guard excludes an app that runs from the DMG only because the image is read-only (`format = "ULMO"` in `scripts/dmg.settings.py`). Do not change it to a writable format such as UDRW.
- **Downgrade:** the bundle version must equal the offered version, and the offered version is newer than the running one (from `newer_release`). `download_app_update` itself accepts any version; the guarantee holds because `AppUpdateModel` installs only the `AppUpdate` that its own check returned (Data Flow step 3, S4). An old, validly signed build cannot be installed through this path.
- **Paths:** the download URL derives only from the parsed version (digits and dots), and the staging folder is the fixed `<cache>/app-update/`, so the feed cannot point the download or the unpack outside it. The zip must hold only `Sublate.app` at the top level, and it must be a folder, not a symlink.
- **No privilege escalation:** the app never asks for an administrator password. A folder that is not writable falls back to the release page.

## Verified Assumptions

An investigator checked these on 2026-11-09, on this Mac and in primary sources.

- **A1 — verified.** A running app in a mounted DMG, or in an App Translocation path, sees its parent folder as not writable.
  - DMG: `Sublate-0.3.0.dmg` is ULMO (read-only). Mounted with and without `-readonly`, the volume is `read-only`, and `FileManager.isWritableFile`, `access(W_OK)` and `touch` all fail.
  - Translocation: Apple's Security source (`SecTranslocateShared.cpp`) mounts the translocated folder as nullfs with `MNT_RDONLY`.
  - `SecTranslocateIsTranslocatedURL` is not a public API (no header in the SDK), and Apple says there is no supported way to detect translocation. So use the writability check, not a translocation check.
  - Side effect: a standard (non-admin) user cannot write to `/Applications` (`root:admin 775`), so that user gets the release page.
- **A2 — verified, with a correction.** A non-sandboxed process without `LSFileQuarantineEnabled` writes files with no `com.apple.quarantine` attribute (only `com.apple.provenance`), so Gatekeeper's quarantine check does not run. The pinned requirement is the only identity gate, but not the only signature gate (see Security Considerations). Whether XProtect scans a file that has a provenance tag is not documented; this spec does not depend on it.
- **A3 — verified, with pitfalls.** A running process keeps running after its bundle is renamed or moved to the Trash, and a new bundle at the original path starts as a separate process. Sparkle 2 swaps from a helper process, uses a same-volume temp folder and `renamex_np(RENAME_SWAP)`, touches the new bundle for Launch Services, waits for the old PID to exit, then opens the new app. `BundleReplacer` and `Relauncher` above follow this.
- **A4 — verified.** A `ditto -c -k --keepParent` zip of the stapled 0.3.0 app, unpacked with `ditto -x -k`, passes `codesign --verify --deep --strict`, `xcrun stapler validate`, and `spctl --assess` ("Notarized Developer ID"). The pinned requirement accepts it and rejects Calculator, an ad-hoc signed copy, and a wrong Team ID. The zip is about 93 MB.
- **A5 — verified.** `releases/download/v0.3.0/Sublate-0.3.0.dmg` answers `302` to a signed URL that ends in `200` with the full length. `releases/latest` gives each asset `size` and `digest: "sha256:<hex>"`, and both match the local file.

## Acceptance Scenarios

### Happy Path

- **S1:** Given the latest release `v0.4.0` has an asset `Sublate-0.4.0.zip` with digest `sha256:abcd…` and a `browser_download_url` that points elsewhere, when the release JSON is parsed, then the `AppRelease` has version `0.4.0`, page `https://github.com/pingeplin/sublate/releases/tag/v0.4.0`, and archive sha256 `abcd…`; the archive URL that `GitHubAppReleases` builds for version `0.4.0` is `https://github.com/pingeplin/sublate/releases/download/v0.4.0/Sublate-0.4.0.zip` (not the asset's `browser_download_url`); and `check_app_update` from `0.3.0` returns an `AppUpdate` with `archive_sha256 = Some("abcd…")`.
- **S2:** Given an update `0.4.0` whose sha256 matches a zip that holds only `Sublate.app`, when `download_app_update` runs with a fake feed, then it returns `<cache>/app-update/Sublate.app`, that folder holds the unpacked bundle, the zip is gone, and the feed was asked for version `0.4.0` (so the URL is `https://github.com/pingeplin/sublate/releases/download/v0.4.0/Sublate-0.4.0.zip`).
- **S3:** Given a fake backend whose download calls the listener with `(50, Some(100))` then `(100, Some(100))` and then returns a staged path, when the user installs, then the model state goes `.downloading(update, nil)` (before the first report) → `.downloading(update, 0.5)` → `.downloading(update, 1.0)` → `.installing(update)`, in that order; in each of these states `downloadPage` is nil and `status` is not `.idle` and names `0.4.0`.
- **S4:** Given an installable update `0.4.0` (from the model's own check) and a fake installer that succeeds, when the user clicks **Install and Relaunch**, then the backend's `downloadAppUpdate` gets that same `AppUpdate`, the installer gets the staged path from the backend, version `0.4.0`, and the model's `runningApp` URL, and then `relaunch` is called once with `runningApp` — after `install` returns, never before.
- **S5:** Given a staged bundle and a running bundle in a writable temp folder, and a verifier that accepts, when the live installer installs, then the running path holds the staged bundle's contents, the folder that holds the running bundle holds no other new entry (no backup copy of the old bundle beside it), the old bundle was passed to the injected trash step, the new bundle's modification date is not older than the start of the install, and the staging path no longer holds the bundle.

### Edge Cases

- **S6:** Given the latest release has no `Sublate-<version>.zip` asset, or the asset has `"digest": null`, or a digest of another algorithm (`sha512:…`), when the release is parsed, then the release is still returned with `archive = None` and `check_app_update` returns `archive_sha256 = None`; and given the model is `.available` with `archiveSha256 == nil` and an installer whose `canInstall` is true, `model.canInstall` is false and `state.downloadPage` is the release page.
- **S7:** Given the folder that holds the running bundle is not writable (a read-only temp folder), the live `canInstall(replacing:)` returns false; given a writable temp folder, it returns true. Given the model is `.available` with `archiveSha256 != nil` and a fake installer whose `canInstall` is false, `model.canInstall` is false and `state.downloadPage` is the release page.
- **S8:** Given the state is `.checking`, `.downloading` or `.installing`, when `check()` or `install()` is called again, then it does nothing (no second backend or installer call, and the state does not change). Given the state is not `.available` with `canInstall` true (for example `.upToDate`, `.installFailed`, or `.available` with no archive), when `install()` is called, then it does nothing.
- **S9:** Given the staging folder holds files from an earlier, interrupted download or a failed install, when `download_app_update` runs, then it removes them first and `<cache>/app-update/` then holds only the new `Sublate.app`.
- **S10:** Given the listener reports `(n, None)` or `(n, Some(0))`, then the state is `.downloading(update, nil)` (indeterminate), and the flow still reaches `.installing(update)` and calls `relaunch`.

### Error Scenarios

- **S11:** Given the downloaded zip does not match `archive_sha256`, when `download_app_update` runs, then it fails with `Sublate update failed: release 0.4.0 does not match its checksum`, and `<cache>/app-update/` exists and holds no entries.
- **S12:** Given the zip holds something other than exactly one top-level `Sublate.app` folder (for example `Other.app`, `Sublate.app` plus `extra`, or `Sublate.app` as a symlink or a plain file), when it is unpacked, then `download_app_update` fails with a `Sublate update failed:` message and `<cache>/app-update/` exists and holds no entries.
- **S13:** Given `download_app_update` is called with `archive_sha256 = None`, then it fails with `Sublate update failed: release 0.4.0 has no Sublate-0.4.0.zip`; given it is called with a version that is not digits and dots (for example `../evil`), then it fails with `Sublate update failed: '../evil' is not a Sublate version`. In both cases the feed is not asked to download.
- **S14:** Given a staged bundle that is unsigned, ad-hoc signed, or signed by another team (for example a copy of `/System/Applications/Calculator.app`), when `BundleVerifier` checks it, then it is rejected, and the live installer's `install` throws and leaves the running bundle unchanged (same files, same contents).
- **S15:** Given a staged bundle whose signature check passes (the signature part of `BundleVerifier` stubbed to accept) and whose `CFBundleShortVersionString` is not the offered version, when the installer installs, then it throws an error whose message names both versions, and the running bundle is unchanged.
- **S16:** Given the replacer's injected file operations fail at the step after the old bundle was moved away (the move of the new bundle into place), when the install runs, then `install` throws and the old bundle is back at the running path, byte for byte. If the old bundle cannot be put back either, `install` throws an error that names where the old bundle is, and that bundle still exists there. If moving the old bundle to the Trash fails after a successful swap, the old bundle is kept, not deleted. The replacer never deletes the old bundle.
- **S17:** Given the download or the install fails, when the model handles the error, then the state is `.installFailed(update, message)` where `message` is the error's `userMessage` (for a backend error, its `Sublate update failed: …` text), `state.status == .failure(message)`, `state.downloadPage` is the release page, `model.canInstall` is false, and `relaunch` is not called.
- **S18:** Given the network fails during the download, then `download_app_update` fails with a `Sublate update failed:` message and `<cache>/app-update/` exists and holds no entries.

### Running Job Guard

- **S20:** Given an installable update and a fake `JobActivity` whose `isBusy` is true, then `model.isBlockedByJob` is true and `model.canInstall` is still true; when `install()` is called, nothing happens (no backend download call, no installer call, state stays `.available`). When `isBusy` becomes false, `isBlockedByJob` is false and `install()` runs the flow of S4.
- **S21:** Given `install()` started with no job running, and the fake `JobActivity` becomes busy before the install returns, when the install succeeds, then the state is `.readyToRelaunch(update)` and `relaunch` is not called. A call to `model.relaunch()` while still busy does nothing; after `isBusy` becomes false, `model.relaunch()` calls `installer.relaunch(runningApp)` once.

### Release Process (manual check, not unit tests)

- **S19:** Given `make release` runs, then `dist/Sublate-<version>.zip` exists beside the DMG; `ditto -x -k` of it gives one `Sublate.app` that passes `codesign --verify --deep --strict`, `xcrun stapler validate`, and `codesign --verify -R='<pinned requirement>'`.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best — blueprint does not prescribe order, cadence, or commit structure. Only the result is checked. Write tests to the project's conventions and to these principles (the same ones `/verify` scores against — see `references/test-desiderata.md` and `references/anti-patterns.md`):

- **Behavioral over structural** — assert observable output/effects, not internals; the suite must survive refactoring.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant, no tautologies (AP-2, AP-4).
- **Deterministic, isolated, readable** — inject clocks/randomness, no cross-test state, AAA structure with inline setup.

## Definition of Done

Done is when `/verify` passes against this spec:

- [ ] Test suite is green (`make test`).
- [ ] Every acceptance scenario (S1…S18, S20, S21) maps to at least one test; S19 is checked by hand on a `make release` build.
- [ ] No covered-but-vacuous scenarios — each scenario's test fails under the smallest break of its behavior (thought-mutation).
- [ ] Tests meet the Desiderata bar (Behavioral and Structure-insensitive first); no AP-1…AP-8 violations.
- [ ] No implementation-quality blockers (stubs, dead code, stale docstrings). `README.md` and the Settings footer describe the new flow.

## Trade-offs and Limitations

- Users on 0.3.0 or earlier must update by hand once.
- An app installed in a folder that needs an administrator password (for example `/Applications` for a standard user without write access) cannot update itself; the user gets the release page.
- Each release uploads two copies of the app: the DMG (about 73 MB) and the zip (about 93 MB).
- The old bundle goes to the Trash after a successful update. This keeps a way back, but the Trash grows by one copy of the app per update until the user empties it.
- The sha256 digest comes from the same place as the file; the signature check carries the trust.
- The download has no cancel button. Quitting the app stops it; the next install empties the staging folder (S9).
- A running job blocks the install and the relaunch (S20, S21). A job that starts during the download does not stop the download; the relaunch then waits for the user.
- The app checks for its own updates only when the user asks, as today. An automatic check is out of scope (decided 2026-11-09).
