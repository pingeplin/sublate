# 2611.0002 Video Progress Stages

**Date:** 2026-11-17
**Status:** implemented
**Author:** EP Lin

## Context

The video row in the Progress section shows one bar and one label. Today:

- `core/src/ytdlp.rs` (`YtDlp::download_video`) passes `--progress-template "download:CT_PROGRESS %(progress._percent)s"` and calls `on_progress(f32)` for each tagged line.
- `core/src/services.rs` (`download_video`) maps every yt-dlp percent to `VideoStage::Downloading`. For `VideoFormat::AppleCompatible` it then runs `AppleConverter::convert` (`core/src/apple_convert.rs`) and maps its percent to `VideoStage::Converting`.
- `core/src/ffi.rs` exports `VideoProgressListener::on_video_progress(stage: VideoStage, percent: f32)`.
- `app/Kit/Sources/SublateUI/JobState.swift` holds `struct VideoProgress { stage, percent }`. `Views/ProgressSection.swift` draws `ProgressView(video.label, value: video.percent, total: 100)`.
- `ProgressChannel` (`ProgressChannel.swift`) buffers with `.bufferingNewest(1)`: a slow consumer skips older values.

Verified with yt-dlp 2026.10.26 (the default format, `-f b`, and `--load-info-json -` with `-S lang,height:720,vcodec:h264,acodec:aac`):

1. `--print "before_dl:<tag> %(format_id)s"` prints once before the download, for example `395+251` (two streams) or `18` (one file). It does not turn on `--simulate`.
2. In a progress template, `%(info.format_id)s` is the format of the stream that downloads now. The streams download in the order of `format_id` (`395` first, then `251`). `%(progress.downloaded_bytes)s` and `%(progress.total_bytes)s` are numbers or `NA`. `%(progress.total_bytes_estimate)s` can also be `NA`.
3. `%(progress.status)s` is `downloading`, and `finished` on the last line of each stream. The merge, remux and cover-art steps come after the `finished` line of the last stream.
4. A `postprocess:` progress template writes to **stderr**. `process::run` reads only stdout, so the core cannot use it.
5. When a one-file download is already on disk, yt-dlp prints one `finished` line with `downloaded_bytes` `NA`. When the merged file of a two-stream download is already on disk, yt-dlp prints no download line.

## Motivation

With two streams, the bar goes from 0 to 100 % two times under the same label "Video". The user thinks that the download started again. During the merge and the cover-art step the bar stays at 100 %, so the job looks finished when it is not. For Apple devices, a conversion moves the bar back to 0 a third time.

The user must see which step runs, how many steps there are, and how far the current step is. The approved mockup: https://claude.ai/artifact/8dqMgqZeSMQVR4V7RGZRCG ("提議：分段式進度").

## Proposed Solution

### Overview

The Rust core keeps the full state of the video job as a list of steps and sends a **full snapshot** of that list with each report. A snapshot replaces the one before it, so the `bufferingNewest(1)` channel can drop any report and the UI is still correct.

The step list is known when yt-dlp prints `before_dl`: one step for each stream, then **Finishing**, then (for Apple devices only) **Converting**. The number of steps does not change after that. When no conversion is necessary, the Converting step becomes **Skipped**, not Done.

The Swift view draws a step strip (one segment per step) and, below it, the title, the detail, and a bar for the current step. A step with no percent shows a bar with no value (indeterminate).

### Key Components

- **`core/src/video_progress.rs`** (new) — the uniffi types below and a `VideoTracker` that turns download events into snapshots. No I/O. Replaces `VideoStage` in `video_format.rs`.
- **`YtDlp::download_video`** (`core/src/ytdlp.rs`) — adds the `before_dl` print, extends the `download` template, and reports `DownloadEvent`s instead of `f32`.
- **`AppleConverter::convert`** (`core/src/apple_convert.rs`) — returns `AppResult<bool>`: `true` when it replaced the file, `false` when the streams were already accepted.
- **`track_video`** (`core/src/video_progress.rs`) — owns a `VideoTracker` for one job. It runs the download and the conversion through the `VideoWork` trait, sends each changed snapshot, and on an error marks the running step `Failed` before it returns the error. `AppState::download_video` (`core/src/services.rs`) gives it a `VideoJob` that calls `YtDlp` and `AppleConverter`.
- **`VideoProgressListener`** (`core/src/ffi.rs`) — `on_video_progress(progress: VideoProgress)`.
- **SublateUI** — deletes the Swift `struct VideoProgress` (the generated record takes its name), adds presentation (labels, title, detail) in an extension, and redraws `ProgressSection`. `ContentModel.getContent` starts the row as `VideoProgress(steps: [])`.

### Data Flow

1. `ContentModel.getContent` sets `progress.video = VideoProgress(steps: [])`. The view shows "Preparing…" with an indeterminate bar.
2. yt-dlp prints the `before_dl` line. `YtDlp` sends `DownloadEvent::Streams { format_ids }`. The tracker builds the step list, all `Waiting`. A second `Streams` event (the fallback to a new page extraction in `YtDlp::download`) builds the list again from the start.
3. Each tagged download line becomes `DownloadEvent::Stream { format_id, finished, percent, bytes }`. The tracker sets all stream steps before that stream to `Done`. A line that is not `finished` sets the stream's step to `Running`. A `finished` line sets it to `Done`.
4. When the `finished` line is for the last stream in the list, the tracker also sets Finishing to `Running { percent: None, bytes: None }`.
5. When yt-dlp exits with success, all stream steps and Finishing become `Done`.
6. Apple devices only: Converting becomes `Running { percent: None, bytes: None }` while ffprobe runs, then `Running { percent: Some(p), bytes: None }` for each ffmpeg report. When `convert` returns, Converting becomes `Done` (`true`) or `Skipped` (`false`).
7. On any error, the step that is `Running` becomes `Failed`, the snapshot is sent, and the error goes back to Swift. `ContentModel.status` becomes `.failure` with the error message, as today.

### Interface Contract

```rust
// core/src/video_progress.rs — exported with uniffi
pub enum VideoStep { Video, Audio, VideoWithAudio, Finishing, Converting }

pub struct ByteProgress { pub done: u64, pub total: Option<u64> }

pub enum StepState {
    Waiting,
    Running { percent: Option<f32>, bytes: Option<ByteProgress> },
    Done,
    Skipped,
    Failed { percent: Option<f32>, bytes: Option<ByteProgress> },
}

pub struct VideoStepProgress { pub step: VideoStep, pub state: StepState }

/// A full snapshot. `steps` is empty until yt-dlp names the streams.
pub struct VideoProgress { pub steps: Vec<VideoStepProgress> }

// internal to the core, not exported with uniffi
pub enum DownloadEvent {
    /// From the `before_dl` line. `format_ids` is the `format_id` split on `+`, in order.
    Streams { format_ids: Vec<String> },
    /// From a tagged download line. `percent` is `None` when `_percent` is `NA`.
    Stream { format_id: String, finished: bool, percent: Option<f32>, bytes: Option<ByteProgress> },
}

// core/src/ffi.rs
pub trait VideoProgressListener: Send + Sync {
    fn on_video_progress(&self, progress: VideoProgress);
}
```

Stream steps from the `format_id` list: two ids → `[Video, Audio]`; one id → `[VideoWithAudio]`. Any other count → one `VideoWithAudio` step for each id. A download line whose `format_id` is not in the list is ignored.

`bytes.total` is `total_bytes`, else `total_bytes_estimate`, else `None`. `bytes` is `None` when `downloaded_bytes` is `NA`.

Swift presentation (English, as the rest of the app):

| Step | Strip label | Running title |
|---|---|---|
| `Video` | Video | Downloading video stream |
| `Audio` | Audio | Downloading audio stream |
| `VideoWithAudio` | Video | Downloading video |
| `Finishing` | Finishing | Merging streams and adding cover art |
| `Converting` | Converting | Converting for Apple devices (no percent: Checking streams for Apple devices) |

- Running title line: `Step <n> of <count> · <running title>`. `<n>` is the 1-based position of the `Running` step in `steps`. `<count>` is the length of `steps`, `Skipped` steps included.
- Detail: `<percent rounded down>%` (for example `29.9` gives `29%`), plus ` · <done> of <total>` when bytes are known (sizes from `ByteCountFormatter.string(fromByteCount:countStyle: .file)`; `<done>` only when the total is unknown). No percent: `Working…`.
- All steps `Done` or `Skipped`: title `Done`, full bar. A `Skipped` step shows `Not needed` as its strip label.
- A `Failed` step: title `Step <n> of <count> · Failed: <running title>`, where the running title follows the `percent` that `Failed` carries (for `Converting`). Detail: as for a `Running` step, but `Stopped` instead of `Working…`. Bar: the last percent, or empty when `percent` is `None`.
- Steps known, none `Running` or `Failed`, not all `Done`/`Skipped`: title `Starting…`, empty detail, indeterminate bar.
- `Done` title: empty detail.
- Empty `steps` while the job runs: title `Preparing…`, indeterminate bar. Empty `steps` after the job ended (yt-dlp failed before `before_dl`): title `Stopped`, empty bar. `ProgressSection` gets `ContentModel.isDownloadingVideo`, which is `true` only while the video download runs (not while the subtitles still translate, and not during a fetch), to tell the two apart.
- `percent: None` with bytes known: detail `<done> of <total>` (or `<done>`).
- The indeterminate bar is a linear bar (`.progressViewStyle(.linear)`), not a spinner.

Breaking change: the uniffi listener signature and `VideoStage` go away. The Swift bindings must be generated again (`make core`, which runs `uniffi-bindgen-swift --swift-sources`).

## Alternatives Considered

### Separate "plan" and "progress" callbacks

Smaller messages, but `ProgressChannel` keeps only the newest value, so the plan can be dropped. A snapshot has no such failure mode.

### Add the Converting step only when a conversion starts

The count goes from "of 3" to "of 4" during the job. The user asked for a clear and stable state. A `Skipped` step keeps the count stable and tells the truth.

### Start Finishing on a `postprocess:` progress template

yt-dlp writes these lines to stderr, which `process::run` does not stream (verified). The `finished` status of the last stream gives the same moment on stdout.

### Find the stream kind from `vcodec`/`acodec` on each download line

It also works (verified), but the labels must be known when the list is built, before the first download line. The `format_id` order is enough and is simpler.

## Acceptance Scenarios

### Happy Path
- **S1:** Given yt-dlp prints `before_dl` `395+251`, when the tracker gets that event, then the snapshot has steps `[Video, Audio, Finishing]`, all `Waiting`.
- **S2:** Given the steps of S1, when a download line for `251` at 30 % with 1 100 000 of 3 600 000 bytes comes, then `Video` is `Done`, `Audio` is `Running { percent: Some(30.0), bytes: Some(ByteProgress { done: 1100000, total: Some(3600000) }) }`, and `Finishing` is `Waiting`.
- **S3:** Given `Audio` is running, when the `finished` line for `251` (the last stream) comes, then both stream steps are `Done` and `Finishing` is `Running { percent: None, bytes: None }`.
- **S4:** Given a fake yt-dlp script that prints, in the format of the templates that `download_video` passes: `before_dl` `395+251`; a `downloading` line for `395` at 50 with 1024 of 2048 bytes; a `finished` line for `395` at 100; a `finished` line for `251` at 100 with `NA` bytes; and the path. When `YtDlp::download_video` runs, then it reports exactly these events in this order: `Streams { ["395", "251"] }`, `Stream { "395", finished: false, Some(50.0), Some({1024, Some(2048)}) }`, `Stream { "395", finished: true, Some(100.0), .. }`, `Stream { "251", finished: true, Some(100.0), None }`, and it returns the path.
- **S5:** Given `VideoFormat::AppleCompatible` and a converter that converts, when the job ends, then the last snapshot has every step `Done`, the last one `Converting`.
- **S6:** Given the Swift view gets a snapshot `[Video Done, Audio Running { percent: Some(30.0), bytes: Some({1100000, Some(3600000)}) }, Finishing Waiting]`, then the title is `Step 2 of 3 · Downloading audio stream` and the detail is exactly `30% · <F(1100000)> of <F(3600000)>`, where `F` is `ByteCountFormatter.string(fromByteCount:countStyle: .file)`.
- **S17:** Given `VideoFormat::AppleCompatible` and `before_dl` `395+251`, when the tracker gets that event, then the first snapshot has steps `[Video, Audio, Finishing, Converting]`, all `Waiting`.
- **S22:** Given `Finishing` is `Running { percent: None, bytes: None }` in a list of three steps, then the Swift title is `Step 3 of 3 · Merging streams and adding cover art` and the detail is `Working…`.
- **S23:** Given `Converting` is `Running { percent: None, .. }`, then the Swift title ends with `Checking streams for Apple devices`. Given `Converting` is `Running { percent: Some(40.0), .. }`, then the title ends with `Converting for Apple devices`.
- **S24:** Given a snapshot in which every step is `Done` or `Skipped`, then the Swift title is `Done` and the bar value is 100 of 100.
- **S25:** Given `VideoFormat::AppleCompatible` and a converter that reports 40, when the job runs, then the listener gets a snapshot with `Converting` as `Running { percent: None, bytes: None }`, then a later one with `Converting` as `Running { percent: Some(40.0), bytes: None }`, and `Finishing` is `Done` in both.

### Edge Cases
- **S7:** Given `before_dl` prints `18`, when the steps are built, then they are `[VideoWithAudio, Finishing]`.
- **S8:** Given steps `[Video, Audio, Finishing]`, when the `finished` line for `395` (not the last stream) comes, then `Video` is `Done`, and `Audio` and `Finishing` are `Waiting`.
- **S9:** Given `before_dl` `18` and the file already on disk (one `finished` line at 100 with `downloaded_bytes` `NA`), then `VideoWithAudio` is `Done` and `Finishing` is `Running { percent: None, bytes: None }`; when yt-dlp ends with success, the last snapshot has every step `Done`.
- **S10:** Given `VideoFormat::AppleCompatible` and streams that are already accepted, when the job ends, then `Converting` is `Skipped` and the Swift strip label for it is `Not needed`.
- **S11:** Given a second `before_dl` line after some progress (the extraction fallback), then the step list is built again with all steps `Waiting`.
- **S12:** Given `ContentModel.getContent` starts with video, before any report, then the video row title is `Preparing…`.
- **S13:** Given `total_bytes` is `NA` and `total_bytes_estimate` is a number, then `bytes.total` is the estimate.
- **S18:** Given `before_dl` prints three ids (for example `a+b+c`), when the steps are built, then they are `[VideoWithAudio, VideoWithAudio, VideoWithAudio, Finishing]`.
- **S19:** Given a second `Streams` event after `Audio` ran (S11), when a `downloading` line for `395` comes, then `Video` is `Running` and `Audio` is `Waiting`.
- **S20:** Given a download line at 30 % with `downloaded_bytes` 1 100 000 and both `total_bytes` and `total_bytes_estimate` `NA`, then `bytes` is `Some(ByteProgress { done: 1100000, total: None })`, and the Swift detail is exactly `30% · <F(1100000)>`.
- **S21:** Given a `Running` step with percent `29.9` and `bytes: None`, then the Swift detail is exactly `29%`.
- **S26:** Given `before_dl` `395+251` and no download line (the merged file is already on disk), when yt-dlp ends with success, then the last snapshot has every step `Done`.
- **S30:** Given a download line with `_percent` `NA` and `downloaded_bytes` 1 100 000 of 3 600 000, then the step is `Running { percent: None, bytes: Some(..) }` and the Swift detail is exactly `<F(1100000)> of <F(3600000)>`.

### Error Scenarios
- **S14:** Given yt-dlp fails while `Audio` is running, when `download_video` returns the error, then the last snapshot sent shows `Video` as `Done`, `Audio` as `Failed`, and `Finishing` as `Waiting`.
- **S15:** Given ffmpeg fails during the conversion, then the last snapshot shows `Converting` as `Failed`, all earlier steps `Done`, and `ContentModel.status` is `.failure` with the error message.
- **S16:** Given a download line whose `format_id` is not in the `before_dl` list, then no step changes.
- **S27:** Given `Audio` is `Running { percent: Some(30.0), bytes: Some(b) }`, when yt-dlp fails, then `Audio` is `Failed { percent: Some(30.0), bytes: Some(b) }` and the Swift title is `Step 2 of 3 · Failed: Downloading audio stream`, the detail is `30% · <F(done)> of <F(total)>`, and the bar value is 30.
- **S28:** Given `[Video Waiting, Audio Waiting, Finishing Waiting]`, then the Swift title is `Starting…` and the detail is empty. When yt-dlp fails in this state, then `Video` is `Failed { percent: None, bytes: None }` and the detail is `Stopped`.
- **S29:** Given yt-dlp fails before `before_dl` while the subtitles still translate, then the listener gets no snapshot, and while the job is still busy the Swift title is `Stopped`, not `Preparing…`.

## Trade-offs and Limitations

- The stream labels depend on yt-dlp's default order (video first, then audio). A custom `-f` that changes the order shows wrong labels. The app does not pass `-f` today.
- Finishing has no percent. yt-dlp does not report one for its post-processors.
- Each snapshot carries the full list (four steps or fewer for one or two streams), so each report is a few bytes larger.
- The bar goes from 0 to 100 % for each step, not over the whole job. The strip shows the position in the job.

## Resolved Questions

1. **Failed bar and title.** `Failed` carries the last `percent` and `bytes` of the step (see the Interface Contract). See the Swift presentation rules.
2. **Steps known, none running.** `Starting…`, empty detail, indeterminate bar. `Done` has an empty detail.
3. **Error with nothing running.** With steps known, the first step that is not `Done` or `Skipped` becomes `Failed { percent: None, bytes: None }`. With no steps, Rust sends nothing and the view shows `Stopped` once the job ended.
4. **Percent `NA`.** The line gives `percent: None` and is not dropped. The detail shows the sizes when known, else `Working…`.
